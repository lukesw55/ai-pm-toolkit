## 2026-09-16: Review: the pre-registration names a tag, because a file cannot contain its own commit id

You are right, and it is a clean logical defect rather than a wording problem. Rule 3 required the file to record the measured commit, and the order then had that commit created by the very edit that writes it. Every way out of that is bad: leave the edit uncommitted and the final pre-registration is not the tracked artefact the rule demands; commit it and HEAD is a different commit from the one named inside; use a placeholder and the protocol is not executable as written. I took your tag contract. The file is written across two commits. Before the smoke it carries the decision criteria, one keep/fix/simplify/remove condition set per pilot skill plus any critical failure that blocks keep on its own, and the name of the annotated tag the measured iteration will run from; that block is immutable from that commit onward. After the smoke it gains only the factual metadata the smoke established, the harness, the verified harness version and the model, with the criteria untouched. That state is committed and tagged pilot-<harness>-<n>-instrument, and the measured iteration runs from the tag, which gives the run one exact externally resolvable revision without anything naming itself. The 40-character identifier does not vanish, it just lives where it can: record_eval_run.py already writes repo_commit from git rev-parse HEAD into every recorded run, so the report quotes it from the run metadata rather than from the pre-registration. I checked that field exists rather than inventing a new requirement for it. The order of operations follows the same shape, and step 3 now says the smoke is inspected for compatibility only, naming what that means: envelope, provenance sidecar, isolation configuration, probe, harness version, model identifier, session identifier. Not output quality, and not at any later point either. Step 12 already excluded the smoke outputs from the measured report and still does. One sentence in the surrounding paragraph changed with it: keeping the smoke and measured identifiers apart is the operator's job, and so is running the measured iteration from the tag rather than from whatever HEAD happens to be, since the runner compares neither. The active changelog entry carried the old sequence in both places and is corrected with the same contract. The merge gate is unchanged and is not mine: main protection is a repository setting, and it stays an unchecked owner item in .ai/tasks.md alongside private vulnerability reporting. Full docs/REPO_HEALTH.md battery green before the commit. Records and documentation only.
