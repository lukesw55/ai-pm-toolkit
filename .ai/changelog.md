## 2026-09-16: B42 review: a partial pass is not "every assertion passed"

An adversarial review of this branch reproduced a card that contradicts itself. classify() returns false-accept on pass_rate >= 0.8, not on 1.0, so any run where the rate clears the threshold with a check still failing lands there. implicated() then discarded the failing labels and both the markdown and the assertion change printed "Every assertion passed", three sections below a grader table showing the FAIL row. assertion_change.targets came back empty too, so the card named no target at all. Reproduced against the repo's own assertions: pass_rate 0.875, the check that failed being "Does not rank by account size alone", which is the doctrinal guard that fires on exactly the behaviour the labeler called weak. Every one of the 85 blocks has between five and ten checks, so the window is reachable for all of them. The failing assertion was always visible in the grader table, so nothing was hidden; what was wrong is the invariant stated twice afterwards and the target dropped from both the implicated set and the change. implicated() keeps the failing labels for a false accept and the docstring stops asserting an invariant the classifier never guaranteed. assertion_change() targets those checks first and says the pass came from the rate clearing the threshold rather than a clean sheet. The markdown says "N of M assertions passed" and lists them; "Every assertion passed" survives only where it is true. The signal that survives either way, which of the passing checks also pass on the eval's own bad and keyword-only fixtures, is unchanged. An eval whose assertion block is gone now returns a no-assertions outcome instead of a false-reject card telling a human to loosen assertions that do not exist. The parity check in validate_repo.py makes that unreachable in a valid repo, but this script runs against a tree someone is editing, which is the point of the loop. Two regression cases: five assertions with four passing, and an eval with an empty block. 26 cases in the file. Full docs/REPO_HEALTH.md battery green before the commit.

## 2026-09-16: B42: the validator skips generated proposals, not the tree they live in

A proposal quotes a recorded model output verbatim, and that text can carry a backticked path that never existed, or one under skills/*/workspace/, which is gitignored and absent on every other clone. Both documentation checks would then fail for everyone on a dated record of one run. GENERATED_RECORDS scopes the skip to docs/benchmarks/<iteration>/proposals/ only; a report.md or a labels file in the same tree stays checked, because those are live contracts. The generator already keeps workspace paths out of backticks, so this is the second layer rather than the first: the first is that the proposal writes the path bare and inside a fenced block. Five cases in test_validate_repo.py pin the boundary, two inside the skip and three outside it.
