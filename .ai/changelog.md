## 2026-09-16: Review: critical-failure state gets a tracked source for both configurations

Both halves land, and the second is the uncomfortable one: the logic was fine and the evidence it reads did not exist. The signal compares two sets, and the guardrail I wrote last round only required the labelers of the with_skill run to agree on what that run carries, which says nothing about the baseline. Your CF-X case is exact: the same failure in both runs is a flat signal, the same failure seen only under with_skill fires step 1, and both runs merely being labelled does not tell those apart. Checked in the code rather than assumed: SCHEMA is 2 in scripts/label_eval_run.py and a record carries schema, iteration, skill, eval_id, eval_name, config, output_sha256, rubric_version, verdict, classification, verdict_reason, labeler, supersedes and labeled_at, with the ten CLASSIFICATIONS being generic handles such as invented-fact and wrong-decision rather than pre-registered per-skill identifiers. So nothing tracked records which pre-registered failure sat in which configuration, and even the agreement I claimed would have been reconstructed from prose after the fact. That is post-hoc freedom at the strongest veto in the procedure. I took the smaller of your two fixes, documentation and records only, leaving the label schema alone. A tracked adjudication record now lives at docs/benchmarks/<measured-iteration>/critical-failures.md, written by the same labelers from the same recorded outputs, one row per pair per pre-registered critical-failure identifier, with skill, eval, failure, an explicit state for without_skill, an explicit state for with_skill and who adjudicated it. A state is present, absent or unsettled, and unsettled is what the labelers of that configuration write when they do not agree about that failure. The criteria block in rule 3 now gives each pre-registered critical failure a short stable identifier, because the record references them by identifier, and step 10 of the order of operations adjudicates alongside labelling. A pair's critical-failure comparison is settled when every identifier of that skill has an explicit present or absent in both configurations; an unsettled identifier in either column does not settle it, and a contaminated pair never settles because a missing configuration leaves nothing to adjudicate. The guardrail is now that every pair has a settled comparison and no identifier is present under with_skill while absent under without_skill. The signal definition, the skill-level regression term and the negative-control term all say they read the record rather than a labeler's prose, since all three use the same comparison and would have inherited the same ambiguity. Modelling the record turned up one more hole, mine and not in your review, and I fixed the protocol rather than my expectation: with the baseline unsettled and with_skill present, the comparison is undetermined, and my definition would have read it as flat and let the pair count up in the margin, which is missing evidence treated as the value absent, the same defect one layer down. A pair whose comparison is not settled is now unresolved for direction as well, which also folds contamination in, and the guardrail still separately requires every pair in the iteration to be settled, so a skill can hold its direction and still be blocked from useful. Checked by extending the model: CF-X present in both is flat and settled, present only under with_skill is down, present only in the baseline is up, an unsettled baseline is neither settled nor readable as a direction, an unsettled identifier beside a settled one still blocks, a split on the verdict category leaves the comparison settled while the pair stays unresolved, contamination never settles, and all nine state combinations for one identifier give exactly one signal and one settlement.
