Establishing it is defined by what the recorded run contains rather than by judgement: both configurations recorded and labelled, and the labelers of the with_skill run agreeing on which pre-registered critical failures it carries. They may still split on the verdict category, which is a different question. A contaminated pair never establishes it, because a missing configuration leaves nothing to compare against and a mismatched envelope means the recorded output is not the one the instrument describes. I took the narrow guardrail you preferred over requiring no unresolved pair at all, and the difference is declared rather than left for a reader to work out: one contaminated pair in any skill now keeps step 4 from firing, while a pair unresolved only because the labelers split on the category, or because its two signals conflict, still leaves useful reachable, since in both of those the critical-failure state is on the record and a conflict in which a critical failure appeared has already fired step 1. ## 2026-09-16: Review: the negative-control guardrail, and pre-registration by reference

Both land, and the first is a gap the unresolved-pair machinery opened without my noticing. Step 4 required that no negative control be materially worse, and the term was defined as a property of the pair, but the only robustness rule I added asks whether the unresolved set could change a skill's direction. Those are different properties. Your case reproduces against the text: five pairs, three resolved up, one flat, the negative control split or contaminated, human margin three against one unresolved, so the direction holds at three greater than one, the grader side can hold too, the skill counts as materially improved, and the protocol still cannot establish that the control did not get worse, because that pair carries no consolidated verdict. Each of the three pilot skills does carry a negative-control eval, which I checked in the manifests rather than assuming: solid-research-plan-agree, solid-status-update-no-fabricated-objection and legit-arr-exception-scored-cleanly. So the control pair is one of that skill's six, five or four and lands in the same unresolved set as any other. I took your second wording, which keeps the condition local to step 4. The per-pair term is now a negative-control pair is materially worse, and a new term carries the guardrail: the negative controls are clear, meaning every negative-control pair in the iteration is resolved and none of them is worse. Being resolved is half the condition and the reason is written down rather than left to be inferred: a split or contaminated control leaves the direction intact while the guarantee that pair exists to provide goes unobserved, so the run would claim something its evidence does not carry. Step 4 uses the new term, so an unresolved control stops step 4 from firing and the iteration reaches the residual, which is inconclusive. That is what your first option would have produced, without adding a step. On the second point you are right that same file was not literally true: rule 3 defines the pre-registration artefact as docs/benchmarks/<measured-iteration>/pre-registration.md while the aggregate procedure lives in docs/EVAL_PROTOCOL.md, and duplicating a hundred lines would be worse than the imprecision. The opening now says the run-level verdict is pre-registered by reference rather than by copy: the procedure lives in the protocol, the pre-registration file names it in its criteria block, and the annotated tag freezes that version of the protocol together with the criteria. The criteria block gains the field you offered, and one detail of it changed after measurement. You wrote the value as EVAL_PROTOCOL.md with a fragment; BACKTICK_PATH in scripts/validate_repo.py only follows a backticked token that holds a directory separator and no whitespace, and it drops the fragment before resolving, so the whole field inside one pair of backticks is never checked and a bare file name is never checked either. The field is therefore written with the key in plain text and the value alone in backticks, carrying the docs prefix, which is the only one of the three forms the checker resolves; I ran all three to find out. A pre-registration file under docs/benchmarks is scanned by that check like any other document, since only the generated proposal cards skip, so the reference is verified on every run of the validator rather than trusted. Checked by extending the model again: your five-pair skill still holds and still improves materially, and the run is inconclusive rather than useful; the same shape with the control resolved and clear is useful; a resolved control that is worse still blocks; an unresolved control in a skill that is not the improving one blocks as well; a critical-failure regression and a direction that does not hold both still outrank the guardrail; the flat run is still negative whether or not a control is unresolved; and 2916 swept states each return exactly one verdict.
