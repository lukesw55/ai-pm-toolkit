## 2026-09-16: The B25 handoff: what a measured iteration may not change, and the order of operations

docs/EVAL_PROTOCOL.md stays the one protocol. This adds a section to it rather than a second runbook, because two documents describing the same pilot is how they drift apart. I measured what the protocol already covered before writing anything. A fresh isolated session per output, the pairing rule that forbids attributing a difference to the harness when the models differ, one attempt directory per attempt with the failures kept, provenance with argv and version and seed, the per-harness runbook, the per-harness report, labelling, the smoke run and verified_harness_versions were all already there. Three rules were not written down anywhere. The first is that the measurement instrument is frozen for the whole iteration, and the instrument is not only the grader: it is the commit, the manifests and prompts, the expected outputs, the skill bundle and dependency hashes, the assertions, the fixtures, the thresholds, the model, the harness version, the runner arguments and the isolation configuration. Changing any one of them starts a new iteration. This is worth stating now that the proposal loop exists, because applying a proposal mid-iteration swaps the grader underneath outputs already recorded. The second is that a model output is never edited by hand, not even for whitespace, and an output that will not parse is a failed attempt kept as one. The third is that the keep, fix, simplify or remove criteria are pre-registered before any output is read, since criteria chosen afterwards describe the results. The order of operations is twelve numbered steps that sequence what the sections below already specify, and it says so rather than restating them. Two of the steps are new requirements: blind the first human read to the configuration where the tooling allows it and disclose the absence of blinding where it does not, and report paired counts, critical failures, negative controls, grader disagreement, token cost and duration. A closing paragraph sets the honest ceiling. Each skill carries five prompts per harness, so a per-skill rate moves in steps of twenty points and one output changes it. The report gives paired cases and counts, and must not present a percentage over five cases as an estimate with a confidence interval. No authenticated model run happens in this environment and none is implied here. The deterministic dry-run and the full battery are what ran. Full docs/REPO_HEALTH.md battery green before the commit.

## 2026-09-16: B43 review 4: the golden-set claim matches what the default command does

That was wrong in the same direction the review is about, so it did not ship: the all-synthetic case already fails on the rule. Both sentences now say that the rule bites once rows exist, that the empty set is the gap, and that a gate runs check --strict, where a warning fails too. Mirrors regenerated for the reference edit.
